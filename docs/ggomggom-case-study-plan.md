## 1. 소개 방향

**고객의 상담 요청이 실제 접수와 운영으로 이어지도록 만든 클라이언트 웹사이트**로 소개한다. 서비스 소개, 견적 신청, 서버 검증, 접수 메일, 전환 추적, 배포 이후 개선을 하나의 흐름으로 보여준다.

현재 포트폴리오의 `Developer, AX Tutor/Mentor` 포지셔닝 중 제품 개발 역량을 보여주는 사례로 배치한다. AI 활용은 개발 과정의 협업 방식으로 설명하며, 서비스 자체에 AI 기능이 있는 것처럼 표현하지 않는다.

- 프로젝트명: **꼼꼼환경**
- 분류: **Product / 클라이언트 웹사이트**
- 프로젝트 소개: **꼼꼼환경은 유품정리·폐기물처리 업체의 서비스 소개와 온라인 견적 접수를 연결한 웹사이트입니다. 고객은 예상 비용과 작업 전후 사례를 살펴보고, 현장 정보와 연락처를 남길 수 있습니다. 담당자는 접수 내용을 이메일로 확인하고 다음 상담을 준비합니다.**
- 카드 요약: **서비스 안내부터 견적 접수와 담당자 알림까지 연결한 생활환경 서비스 웹사이트**
- 본문 첫 제목 초안: **상담 신청을 실제 접수와 운영으로 연결하다**. 카드와 상세 H1은 기존 공통 필드인 프로젝트명 `꼼꼼환경`을 사용한다.
- 공개 결과물: [gomgom2.kr](https://gomgom2.kr/)
- 저장소: [fullkeem/ggomggom](https://github.com/fullkeem/ggomggom). 2026-10-16 연결된 GitHub 도구에서 **비공개** 확인. 공개 페이지의 GitHub 버튼은 우선 생략하고, 공개 가능한 코드 자료가 정해지면 추가한다.
- 기간: **제작 2주**. 메타데이터에는 `2026`, 본문에는 `제작 2주 · 이후 유지보수`로 표기한다. 후속 운영 작업을 제작 기간에 합산하지 않는다.
- 팀 구성·역할: **1인 프로젝트, 전 범위 담당**. 클라이언트 협의·기획·UI/UX 설계·개발·검증·배포·운영 대응을 담당한 것으로 표기한다. 2026-10-16 사용자 확인 기준이다.

## 3. 상세 페이지 구성

전체를 **개요 → 담당 범위 → 핵심 흐름 → 주요 결정 3개 → 운영 결과** 순서로 읽게 한다. 기술 목록보다 해결한 문제와 판단을 먼저 제시한다.

| 순서 | 보여줄 내용 | 필요한 자료 |
| --- | --- | --- |
| 1. 한눈에 보기 | 업체·서비스, 웹사이트의 목적, 1인 전 범위 담당·제작 2주, 운영 사이트 링크 | 데스크톱 홈 캡처 1장 |
| 2. 상담 신청 흐름 | 서비스·비용·사례 확인 → 3단계 입력 → 서버 검증 → 접수 메일 → 완료 안내 | 모바일 폼 캡처, 짧은 흐름도 |
| 3. 고객에게 맞춘 화면 | 현장사례를 드래그 비교에서 좌우 고정 Before/After로 변경한 이유, 견적 CTA 위계와 모바일 하단 접근 | 현재 현장사례 화면, 변경 이유 요약 |
| 4. 실제 접수와 전환 기준 | 제출 버튼 클릭과 실제 메일 발송 성공을 구분하고, 접수 완료 기준으로 추적을 연결한 결정 | 폼 → API → 메일 → 완료 페이지 흐름도 |
| 5. 출시 후 개선 | 클라이언트 피드백, Safari 과거 날짜 검증 보강, SEO·전환 추적·메일 수신자 설정 대응 | 문제 → 판단 → 수정 → 확인 형식의 짧은 사례 |
| 6. 결과와 회고 | 운영 공개, 기본 접수 메일 수신·전환 이벤트 테스트 확인, 후속 운영 대응과 남은 확인 사항 | 확인된 사실만 서술, 실제 사이트 링크 |

AI 활용은 담당 범위 설명 아래 짧게 넣는다. 1인 프로젝트에서 개발 도구로 AI를 활용했음을 밝힌다. 사용자는 요구사항과 우선순위를 정하고 클라이언트와 협의하며 실제 화면·운영 결과를 확인했고, AI와 구현·문서 조사·검증을 협업했다는 기록 범위로 작성한다.

## 4. 강조할 문제 해결 사례

### A. 입력에서 실제 상담 접수까지

- 문제: 현장 조건을 알아야 상담할 수 있으므로 서비스 소개와 연락 버튼 외에 구조화된 신청 흐름이 필요했다.
- 결정: 처리 유형·물량 / 현장 조건·주소 / 일정·연락처의 3단계로 나누고, 주소 검색·단계별 오류 안내·개인정보 동의 검증을 연결했다.
- 구현: 필요한 시점의 외부 스크립트 로드, Cloudflare Pages Functions의 서버 검증과 Turnstile 확인, Resend 접수 메일, 발송 실패 시 대체 상담 안내.
- 확인: 초기 메일 및 로컬 폼 제출 후 사용자의 실제 수신 확인 기록이 있다. 사진 업로드는 MVP에서 제외했고 사진은 카카오 채널로 보내도록 안내한다.

### B. 무엇을 전환으로 셀 것인가

- 문제: 폼 이동이나 제출 클릭을 접수 완료로 계산하면 오류가 있는 신청도 포함되거나 완료 페이지와 중복 집계될 수 있다.
- 결정: 전화·카카오 클릭과 견적 접수 완료를 구분하고 클라이언트와 기준을 합의했다.
- 구현: 메일 발송 성공 뒤 완료 페이지로 이동하며, 접수 표시가 있는 경우에만 완료 전환 호출을 실행한다.
- 확인: 실제 전환 이벤트 테스트 기록이 있다. 이를 문의 증가·전환율 상승의 사업 성과로 해석하지 않는다. 브라우저 접수 표시를 서버의 완전한 중복 제출 방지로 설명하지 않는다.

### C. 고객 환경과 피드백에 맞춘 개선

- 문제: 모바일 상담 접근, 화면 이동 위치, Safari 일정 입력 등 실제 이용 환경에서 추가 요구가 나왔다.
- 결정: 클라이언트가 원하는 행동과 화면 기준을 먼저 맞춘 뒤 공통 앵커 기준과 날짜 검증을 보강했다.
- 확인: 당시 체크·빌드와 모바일·데스크톱 브라우저 검증 기록이 있다. 수십 차례 수정 목록을 나열하기보다 대표 사례 1~2개로 압축한다.

## 5. 성과 표현 기준

- 우선 사용할 결과: 운영 사이트 공개, 3단계 접수 흐름 구축, 기본 메일 수신 확인, 전환 이벤트 테스트, 배포 이후 요구 반영.
- 이미지 약 35MB → 3.2MB는 2026-05-19 작업 보고서의 **이미지 자산 용량** 수치다. 필요할 때 기록 출처를 붙이고 사용하며, 페이지 로딩 시간이나 전송량이 같은 비율로 개선됐다고 쓰지 않는다.
- 문의 증가율, 매출, 광고 효율, 검색 순위, Lighthouse 점수는 확인된 근거가 없어 넣지 않는다. 사이트의 예약·상담 건수 표시도 개발 성과로 사용하지 않는다.
- 10월 참조 수신자 기능은 코드·모의 테스트·배포 성공이 확인되지만 **실제 참조 메일 수신 여부는 해당 채팅에서 미확인**이다. 초기 기본 메일 수신 확인과 구분한다.
- 로고·현장사진 등 제공받은 자료와 직접 설계·구현한 부분을 구분한다. 계약 금액·클라이언트 대화·실제 접수 개인정보·관리 화면은 공개 자료에 포함하지 않는다.

## 7. 제작 순서와 완료 기준

1. **본문 작성:** 확정한 `1인 전 범위 담당 · 제작 2주`를 기준으로 한국어 본문과 영문 대응 내용을 작성한다.
2. **자료 준비:** 데스크톱 홈, 현장사례, 모바일 견적 화면을 선정한다. 코드와 운영 흐름을 보여주는 간단한 도식을 만든다. 개인정보가 없는 상태로 캡처하고 최종 게시용으로 최적화한다.

5. **게시 전 확인:** `/work`, `/work/ggomggom`, `/en/work`, `/en/work/ggomggom`, 웹 이력서, 사이트맵에서 누락·중복·깨진 링크를 확인한다. 기본/야간 모드와 데스크톱 1440px·모바일 390px에서 이미지·본문·링크·뒤로 이동을 확인한다.
